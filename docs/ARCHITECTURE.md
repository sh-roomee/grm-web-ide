# 구조

## 전체 흐름

```
터미널                     Node 프로세스                        브라우저
------                     ------------                        --------
grmide  ──실행──▶  bin/grmide.js
                      │ 저장소 루트 탐색, 토큰 생성, 포트 확보
                      ▼
                    server/index.js  ──── HTTP ────▶  web (Vue 3)
                      │  ├ server/git.js      git 명령 실행/파싱
                      │  ├ server/diff.js     unified diff → side-by-side 구조
                      │  └ server/watcher.js  파일 감시
                      │
                      └─ SSE /api/events ────────▶  변경 알림 → 화면 자동 갱신
```

## 설계 결정

### 겉모습은 Apple 플랫폼의 재료를 그대로 쓴다

이 도구는 macOS에서 터미널 옆에 띄운다. 그래서 iOS/macOS를 흉내내는 대신 **그 재료를
그대로** 쓴다: 시스템 폰트(SF Pro / SF Mono), iOS 시스템 컬러, 문법 강조는 Xcode 다크
팔레트. 웹폰트를 받지 않으니 로컬 도구답게 즉시 뜨고, OS와 같은 결이 된다.

구조는 **"iOS 껍데기, 터미널 심장"** 으로 갈랐다.

- **크롬**(내비게이션 바·목록·팝오버·시트)은 iOS 문법을 따른다. 반투명 바, 세그먼티드
  컨트롤, 알약 뱃지, inset grouped list, 흐린 시트.
- **코드 영역의 밀도는 건드리지 않는다.** 기본값은 줄 높이 20px, 12.5px 고정폭이다.
  iOS의 넉넉한 여백을 코드에 적용하면 한 화면에 보이는 줄이 줄어 도구가 쓸모없어진다.
  글자 크기는 사람이 바꿀 수 있지만(아래 "코드 표면") 여백 비율은 고정이다.

층은 흐림과 표면 밝기로 만든다: 캔버스(`--bg`) 위에 내용 카드(`--bg-panel`)가 뜨고,
그 위에 반투명 바와 시트가 얹힌다. 그림자는 팝오버·시트에만 쓴다.

### 코드 표면은 캔버스보다 밝다 (2026-07-27)

처음에는 코드도 캔버스(`--bg: #0b0b0d`, 거의 순검정) 위에 그리고 글자는 `--fg`
(`#f2f2f7`, 거의 흰색)를 썼다. 실제로 오래 읽어 보니 눈이 아팠다. 원인이 두 가지였다.

- **팔레트와 바닥이 어긋났다.** 문법 강조는 Xcode 다크를 그대로 쓰는데, 그 색들은
  Xcode 에디터 배경 `#1F1F24`(회색 계열) 위에서 고른 값이다. 채도 높은 색을 순검정에
  얹으면 경계가 번져 보이고(halation) 코드 영역이 화면에 뚫린 구멍처럼 읽힌다.
- **대비가 부족한 게 아니라 과했다.** `#f2f2f7` on `#0b0b0d`는 약 19:1이다. 접근성
  하한을 걱정할 자리가 아니라, 상한을 넘어 눈이 쉬지 못하는 자리였다.

그래서 코드 영역에만 `--bg-code: #1f1f24` / `--fg-code: #dfdfe0`를 두고 Xcode가 원래
쓰는 짝으로 되돌렸다(약 12:1). 캔버스는 그대로여서 코드 영역이 오히려 한 층 떠 보이고,
"표면 밝기로 층을 만든다"는 규칙과도 맞는다.

바닥이 밝아지면 그 위에 얹는 반투명 색은 같은 알파에서 더 약하게 읽힌다(대비는
차이/바닥이다). 그래서 `--diff-add-bg` 계열과 단어 하이라이트 알파를 조금씩 올렸고,
줄번호칸(`--diff-gutter`)은 흰색을 얹어 띄우는 대신 검정을 얹어 가라앉혔다 — 코드가
앞에 와야 한다.

`ReviewSheet`의 인용 조각도 같은 표면을 쓴다. 코드는 어디에 나와도 같은 바닥 위에
있어야 한다.

### 코드 글자 크기는 사람이 정한다 (2026-07-27)

밀도는 이 도구의 전제라 기본값(12.5px / 20px)은 바꾸지 않는다. 다만 고정이면 눈에
맞지 않는 사람에게는 읽을 방법이 없었다.

`--code-font-size` 토큰 하나만 움직이고, 줄 높이·줄번호칸 폭·부호칸은 모두 거기에
비례하게 뒀다(`--row-height: calc(var(--code-font-size) * 1.6)`, 폭은 `em`). 비율
1.6은 12.5px에서 정확히 20px — 지금까지의 밀도다. 그래서 **배율만 바뀌고 짜임새는
같다.** 폭을 px로 박아 두면 17px에서 네 자리 줄번호가 잘린다.

`⌘+`/`⌘-`/`⌘0`은 `preventDefault`로 브라우저 확대를 가로챈다. 브라우저 확대는 바와
목록까지 같이 키워서 한 화면에 남는 코드가 오히려 줄어든다 — 코드 영역만 움직여야
의미가 있다. 범위는 11–17px, 0.5px 단위다(1px씩 가면 작은 크기에서 한 걸음이 크게
튄다). 값은 `localStorage`에 남는다. 파일마다 다시 고르게 하면 쓸 수 없다.

키를 눌러도 화면이 조금씩만 움직여서 눌린 건지 브라우저가 먹은 건지 알기 어렵다.
그래서 바꾼 직후에만 지금 크기를 알리는 배지를 잠깐 띄운다.

`⌥`가 섞인 조합은 받지 않는다. 탭 이동(`⌥←/→`)과 겹치지 않게 한다.

탭에 보이는 이름은 **GRM IDE**로 두고(명령은 `grmide`), 파비콘도 같은 팔레트를 쓴다.
글자를 쓰지 않고 이 도구가 하는 일을 그렸다 — 지운 줄(빨강, 짧다)과 더한 줄(초록, 길다).
16px에서 뭉개지지 않게 막대를 두껍게(5.5/32) 잡고, 어두운 탭 바에서 사각형이 사라지지
않도록 테두리를 한 겹 뒀다. `theme-color`는 캔버스 색과 같게 맞춰 브라우저 크롬이
앱과 이어지게 한다.

좌측 파일 목록을 iOS 설정 앱의 **inset grouped list**로 만든 것이 이 화면의 시그니처다.
44개 파일을 훑는 화면이라 줄이 빽빽하게 이어지면 벽이 되고, 그룹이 카드로 떨어져 있으면
"여기부터 staged"가 눈에 먼저 들어온다. 목록 스캔에 특화된 형태가 이 화면의 일과 맞는다.

선택 행은 꽉 찬 파랑이 아니라 **반투명 강조 + 왼쪽 막대**다(macOS 사이드바 방식).
파일 44개를 오가는 동안 채도 높은 면이 계속 바뀌면 눈이 피곤하다.

### diff 파싱을 서버에서 한다

`git diff` 원문을 브라우저로 보내고 거기서 파싱하는 방법도 있지만 서버에서
side-by-side 행 구조까지 만들어 보낸다.

- AI가 만든 변경은 파일 수가 많다 (44개 파일이 예사다). 파싱과 단어 diff 비용을
  클라이언트에 얹으면 파일 전환이 버벅인다.
- 파서가 순수 함수라 테스트로 고정할 수 있다. 실제로 초기 구현에서 "모든 diff
  끝에 빈 컨텍스트 행이 붙는" 버그를 테스트가 잡아냈다.

### 단어 단위 diff는 LCS 테이블, 결과는 오프셋

토큰(공백/식별자/기호) 단위로 쪼갠 뒤 LCS DP를 돌린다. 한 줄이 400 토큰을
넘으면 건너뛴다 — 미니파이된 한 줄에 DP를 돌리면 멈춘다.

결과를 문자열 조각이 아니라 오프셋 구간 `[[start, end], ...]`으로 보낸다.
문법 강조 토큰과 변경 구간이 서로 걸치기 때문에, 오프셋이 아니면 두 하이라이트를
합칠 수 없다. 아래 항목 참고.

### 문법 강조는 클라이언트 플러그인

모두 흰색으로 나오면 IDE보다 가독성이 떨어진다. 그래서 언어별 플러그인 구조를
두고 전경색으로 칠한다. 배경색은 이미 diff(추가/삭제/변경된 단어)가 쓰고 있어서,
**두 하이라이트가 색 채널을 나눠 쓴다.**

플러그인 규약은 `web/src/highlight/index.js` 주석에 있다. 요지는 한 줄을 받아
`[{ start, end, cls }]`를 돌려주는 함수 하나다. 언어를 추가하려면
`languages/`에 파일을 만들어 등록하고, `server/language.js`의 확장자 표에 같은
id를 넣으면 된다.

언어마다 "그 언어를 읽을 때 눈이 먼저 찾는 것"이 다르다. js 는 키워드·문자열·호출이지만
**java 는 타입과 애너테이션**이다. 그래서 java 플러그인은 `@Annotation` 을 한 덩어리로
떼고 `UpperCamelCase` 식별자를 타입으로 본다 — 자바는 이름 관례가 강해 이 어림짐작이
거의 맞고, 틀려도 색 하나가 다를 뿐이다. 기본형(`int`·`boolean`)은 타입, 리터럴
(`true`·`null`)은 키워드로 나눠 시그니처가 빨리 읽히게 했다.

**왜 서버가 아니라 클라이언트인가.** 강조는 표현의 문제이고, 서버 응답을
언어별 span으로 부풀리면 페이로드가 몇 배로 커진다. 나중에 가상 스크롤을
넣으면 보이는 줄만 칠하면 되므로 클라이언트가 맞는 자리다.

javadoc 중간 줄(`* @param …`)은 예외로 뒀다. 줄 단위라 블록 중간을 모르는 것이 원래
한계인데, 자바는 파일마다 클래스 위에 javadoc 이 붙어 그 한계가 **첫 화면부터** 보인다.
그래서 `^\s*\*` 로 시작하는 줄은 주석으로 칠한다. 자바에만 두는 이유는 JS 라면
`*next() {}`(제너레이터)일 수 있지만 자바에는 그 문법이 없어서다.

**왜 줄 단위 무상태인가.** diff는 파일의 조각만 보여주므로 애초에 완전한 문맥이
없다. 줄 단위로 끊으면 훨씬 단순하고, 대가로 여러 줄에 걸친 주석이나 템플릿
리터럴이 가끔 틀리게 칠해진다. 뷰어에서는 감당할 수 있는 오차다.

여러 줄 태그처럼 자주 나오는 경우는 되짚기로 보완했다. 이어지는 줄이
`:key="..."` 로 시작하면 태그 안이라고 판단한다 — Vue 템플릿에서 흔한 모양이다.

### .vue 구획 판단만 서버가 한다

`.vue` 한 파일에 markup / javascript / css가 섞여 있어서, 어떤 줄을 무엇으로
칠할지 알아야 한다. 그런데 diff에 담긴 조각만으로는 `@@ -249,7 @@` 짜리 훅이
`<script>` 안인지 알 수 없다 — `<script>` 태그 줄이 화면에 없기 때문이다.

그래서 서버가 워킹트리의 파일 전체를 훑어 블록 경계만 뽑아 `sections`로 보낸다.
전체를 토크나이즈하는 게 아니라 1열의 `<template>` / `<script>` / `<style>`만
찾는 가벼운 스캔이다.

좌우 줄 번호가 어긋나는 만큼 블록 경계 부근에서 틀릴 수 있지만, 양쪽 버전을
따로 읽는 비용을 아끼는 편이 낫다고 판단했다.

### 실시간 갱신은 폴링이 아니라 SSE

IDE는 창에 포커스를 줘야 갱신되고, 그게 오히려 방해가 된다. 이 도구의 사용자는
터미널에 손을 두고 브라우저를 곁눈질한다. 따라서 파일이 바뀌면 서버가 밀어준다.

- `.git` 디렉토리 전체는 감시에서 제외하되 `index`, `HEAD`, `MERGE_HEAD`,
  `ORIG_HEAD`는 개별 감시한다. stage, 브랜치 전환, 머지 진입은 워킹트리 파일을
  건드리지 않고도 화면을 바꿔야 하는 이벤트다.
- `node_modules`, `dist` 같은 디렉토리는 감시하지 않는다. AI가 파일을 연달아
  쓰는 동안 이벤트가 폭주하므로 200ms 디바운스로 묶는다.
- WebSocket이 아니라 SSE인 이유: 서버→클라이언트 단방향으로 충분하고,
  HTTP 하나로 끝나서 인증/프록시 설정이 따로 필요 없다.

### 재접속은 브라우저에 맡기지 않는다

`EventSource`의 자동 재접속을 쓰지 않고 직접 돌린다(`web/src/api.js`). grmide를
끈 뒤 브라우저가 재접속을 반복하면서 **페이지가 먹통이 되는 것을 실제로 겪었다.**
`retry` 값을 늘려도 재현됐다.

지금은 error가 나면 즉시 닫고 1·2·4·8·16초 간격으로 다섯 번만 시도한 뒤
포기한다. 그 뒤에는 상단에 "다시 연결" 버튼을 띄우고 사용자가 누를 때까지 멈춘다.

끊긴 상태를 상단에 반드시 표시한다. 서버가 죽었는데 옛 내용이 그대로 보이면
지금 상태로 착각한다 — 실시간 갱신을 전제로 만든 도구에서는 이게 제일 위험하다.

### 종료할 때 SSE 연결을 먼저 끊는다

`server.close()`는 열려 있는 연결이 끝나기를 기다린다. SSE는 스스로 끝나지 않으므로,
연결을 먼저 끊어주지 않으면 **브라우저 탭이 열려 있는 동안 Ctrl-C로 grmide가
종료되지 않는다.** 실제로 이 상태에 빠졌었다.

그래서 종료 시 순서가 있다: 모든 SSE 응답을 `end()` → `closeAllConnections()` →
`server.close()`. 그래도 남는 연결이 있으면 1초 후 그냥 나간다. 두 번째 Ctrl-C는
즉시 종료다.

### 그래프는 숫자로 보내고 그림은 클라이언트가 그린다

`git log --graph`의 ASCII 그림을 그대로 옮기지 않는다. 서버는 각 커밋이 몇 번째
레인에 있고 어떤 선이 그 행을 지나가는지를 숫자로 내보내고(`lane`, `lanesAbove`,
`lanesBelow`, `parentLanes`), 클라이언트가 SVG로 그린다.

ASCII를 파싱하는 쪽이 짧아 보이지만, `|/`·`|\`·`|_` 조합을 되짚어 위상을
복원하는 일이 되고 git 버전에 따라 모양도 바뀐다. 부모 관계에서 레인을 직접
계산하는 편이 오히려 단순하고, 순수 함수라 테스트로 고정할 수 있다.

레인 계산은 "아래로 이어지길 기다리는 선"의 배열을 들고 도는 방식이다. 커밋을
만나면 그 커밋을 기다리던 레인이 그 자리가 되고, 첫 부모가 자리를 이어받고
나머지 부모(병합)는 다른 레인으로 갈라진다. 비워진 레인은 재사용해서 그래프 폭이
무한정 늘지 않게 한다.

### 읽기는 넓게, 쓰기는 좁게 — 선은 편집에 있다

2026-07-25에 범위를 다시 그었다. 처음에는 "파일 트리 브라우징 금지, 변경된 파일만"
이었는데, diff만으로 판단이 안 되는 순간이 계속 나왔다. 바뀐 줄의 앞뒤가 아니라
그 함수를 쓰는 다른 파일을 봐야 하고, 그러려고 IDE를 켜면 이 도구의 존재 이유가
사라진다.

그래서 **편집이 없는 읽기 전용 IDE**를 기준선으로 삼았다:

- **git이 아는 파일만** 다룬다. 목록은 `git ls-files`, 검색은 `git grep`.
  파일시스템을 직접 훑지 않으므로 `.gitignore`가 자동으로 지켜지고(`node_modules`가
  결과를 덮지 않는다) 도구가 "git이 보는 세계"에 머문다.
- **디렉토리 트리는 처음에 금지였다가 2026-07-29에 허용했다.** "파일에 도달하는
  길은 검색뿐"으로 두 해 봤는데, 코드를 읽다 보면 어쩔 수 없이 다른 파일을
  따라가게 되고, 이름을 모르는 파일은 검색으로 도달할 수 없다. 검색은 "아는
  파일로 가는 길", 트리는 "모르는 파일을 발견하는 길"이라 서로 대신하지 못한다.
  트리도 `git ls-files` 기반이라(위 항목) 파일시스템을 훑지 않는다. "파일
  관리자가 된다"는 걱정이 원래 금지의 이유였는데, 그걸 막는 것은 트리의 부재가
  아니라 쓰기의 부재다 — 읽기 전용이면 트리가 있어도 에디터가 되지 않는다.
- **원격은 fetch와 fast-forward pull만** (2026-07-29, 그 전에는 전부 금지).
  히스토리를 보는 도구가 원격을 못 가져오면 낡은 그림을 보게 된다 — 가져와서
  읽는 것은 읽기의 연장이다. 선은 "히스토리를 다시 쓰는가"에 긋는다: fetch는
  refs만 옮기고, `pull --ff-only`는 이미 있는 커밋으로 포인터만 옮긴다. 갈라져
  있으면 아무것도 바꾸지 않고 실패하며, 머지·리베이스 판단은 터미널로 보낸다.
  push도 넣지 않는다 — 실수의 비용이 비대칭이다(가져오기는 되돌릴 수 있지만
  밀어낸 것은 남의 저장소에 남는다). 실행 UI는 통합 검색의 **액션**이다 —
  전용 버튼을 만들 만큼 잦은 일이 아니고, 이름으로 실행하는 자리는 이미 있다.

### 브랜치 비교는 merge-base 기준이다

`↔ 비교`는 `git diff base HEAD`(두 점)가 아니라 merge-base → HEAD(세 점 의미론)를
쓴다. 두 점은 base가 그동안 전진한 것까지 "이 브랜치의 변경"처럼 보여주는데, 그
거짓은 화면만 봐서는 알 수 없다 — 그럴듯한 diff가 뜨기 때문이다. GitHub PR과 같은
의미론이고, `test/compare.test.js`가 이 약속을 못 박는다(기준이 전진해도 브랜치가
만진 파일만 나온다).

커밋된 것만 본다. 아직 커밋 안 된 수정은 변경사항 화면의 몫이라, 섞으면 "이건
어느 쪽 변경인가"가 생긴다. 화면은 변경사항 레이아웃을 재사용하고(ChangeList
readonly + DiffViewer), 파일은 `compare` 종류의 탭(`B`)으로 쌓인다. diff 요청의
파라미터는 `against`다 — 기준점의 옛 파라미터가 `base=1`이라 이름을 갈랐다.

### 기준점 — git에 없는 "리뷰 시점"을 만든다

git에는 `HEAD`와 index만 있고 "내가 마지막으로 확인한 시점"이라는 개념이 없다.
AI가 20분 동안 계속 고치는 동안 `git diff`는 매번 전체를 다시 보여주고, 이미 본
40개 파일과 새로 바뀐 3개가 구분되지 않는다. **이 도구가 IntelliJ보다 결정적으로
나을 수 있는 지점이 여기다** — IntelliJ의 Local History는 파일별·시간순이고 리뷰
시점이라는 개념이 없다.

구현은 git 객체 모델을 그대로 쓴다:

```
GIT_INDEX_FILE=.git/grmide-index git add -A && git write-tree   → 트리 sha
git update-ref refs/grmide/baseline <tree>
git diff-tree -r <baseline> <현재 트리>                          → 새로 바뀐 것만
```

- **별도 index 파일**을 쓴다. 사용자의 index를 건드리면 stage 상태가 망가진다.
  그 파일을 지우지 않고 재사용하는 이유는 git의 stat 캐시다 — 빈 index로 시작하면
  저장소 전체를 다시 해시해서 큰 저장소에서 몇 초가 걸린다.
- **ref에 매단다.** 트리 객체만 만들면 참조되지 않아 `git gc`에 사라진다.
  `refs/grmide/*`는 `--all`에 포함되지 않으므로 히스토리 그래프도 오염되지 않는다.
- **트리끼리 비교한다.** `git diff <tree>`는 index에 없는 경로를 비교 대상에서
  빼기 때문에 새로 생긴 untracked 파일이 누락된다.
- 기준점이 없으면 비교를 아예 하지 않는다. 이 기능을 안 쓰는 사람은 비용이 0이다.

### 새 변경 = 기준점 이후 바뀜 AND 아직 확인 안 함

기준점만으로 정하면 개별 확인(`✓ 확인`)을 눌러도 표시가 남는다. 그래서 서버가
알려주는 `fresh`와 클라이언트의 확인 체크를 함께 본다. 기준점은 "무엇이 새로
바뀌었나"를, 확인 체크는 "사람이 무엇을 받아들였나"를 담당한다.

개별 확인은 Cursor를 참고했다. 누르면 **다음 새 변경으로 자동으로 넘어간다** —
44개를 훑을 때 필요한 건 그 반복뿐이다.

### 검색은 추적되지 않은 파일도 본다

`git grep`은 기본적으로 추적 중인 파일만 훑는다. 그러면 **AI가 방금 만든 파일이
검색에서 빠진다** — 이 도구를 쓰는 상황에서 가장 자주 찾을 대상이 안 나온다는 뜻이다.
그래서 `--untracked`를 붙인다. `.gitignore`는 그대로 지켜지므로 `node_modules`가
결과를 덮지도 않는다.

### 이미지는 diff 대신 그림을 보여준다

png을 바꾸면 `git diff`는 "Binary files differ" 한 줄을 준다. 터미널에서 이걸 확인할
방법이 없어서, 이미지가 섞인 변경은 그동안 통째로 판단을 미루는 구간이었다.

**확장자로 판단한다.** 내용을 스니핑하면 "이 바이트열이 정말 png인가"를 판정하는
일이 되고, 틀리면 브라우저에 잘못된 Content-Type을 내보낸다. 표에 없는 확장자는
미리보기를 하지 않는다 — 임의 파일을 임의 타입으로 흘리지 않기 위해서다.

**리비전은 클라이언트가 정하지 않는다.** `/api/blob`은 rev를 받지 않고, diff를
요청할 때와 같은 파라미터(`sha`·`staged`·`base`·`untracked`)를 받아 서버가 이전/이후를
해석한다. 임의 리비전 읽기 엔드포인트가 되지 않고, 화면에서 보고 있는 것과 어긋날
수도 없다. 그래서 "기준점 이후"를 누르면 이미지도 **기준점 시점의 그림**과 비교된다 —
AI가 20분 동안 에셋을 세 번 바꿨을 때 마지막 한 번만 보는 길이다.

**svg는 `<img>`로만 그린다.** 문서에 직접 심으면 svg 안의 스크립트가 실행된다.
svg는 텍스트라 diff도 되므로 `미리보기` 토글로 두 쪽을 오간다. 기본은 그림이다 —
svg를 열어 보는 이유는 대개 "어떻게 생겼나"다.

**픽셀 크기는 서버가 재지 않는다.** 브라우저가 그림을 받으면 아는 값
(`naturalWidth`)이라 서버가 이미지를 디코딩할 이유가 없다. 대신 **바이트 수**는
서버가 `cat-file -s`로 싸게 알 수 있어 diff 응답에 함께 넣는다. 용량 변화와 픽셀
변화는 diff 텍스트로 절대 보이지 않는 정보라 화면 위에 띠로 알린다 — 에셋이 조용히
열 배가 되는 일은 실제로 자주 일어난다.

### 좁은 폭에서는 한 줄로 본다

이 도구의 전제는 **"터미널 옆에 브라우저"** 다. 그 폭은 700~900px인데, side-by-side는
컬럼 하나에 350px 남짓을 주므로 양쪽이 다 잘려 아무것도 읽히지 않았다. 전제와 기능이
어긋난 지점이라 한 줄 보기(inline)를 넣었다.

세 가지를 정했다.

**번호 컬럼은 하나다.** GitHub의 unified diff는 옛/새 번호를 둘 다 보여준다. 여기서는
부호가 가리키는 쪽의 번호만 쓴다 — `−`는 HEAD 쪽 번호, `+`와 문맥은 지금 파일의 번호.
껍데기가 106px(52+52)에서 60px(46+14)로 줄고 그 차이가 그대로 코드 폭이 된다. 폭을
벌려고 만든 기능인데 껍데기를 두 벌 유지하면 이유가 사라진다. 부작용으로 코멘트가
달릴 쪽도 줄마다 하나로 정해져 오히려 단순해졌다.

**처음 열 때만 폭으로 정한다.** 1100px 미만이면 한 줄 보기로 시작하고, 사용자가 한 번
고르면 `grmide:diffLayout`에 저장해 그 뜻을 지킨다. 창 크기에 따라 계속 바뀌면 내가
고른 것이 언제 무시될지 몰라 신뢰할 수 없는 화면이 된다.

**찾기 번호는 보기 방식에 딸린다.** `data-hit` 번호는 화면에 그려지는 순서를 따라야
한다. 한 줄 보기의 문맥 줄은 오른쪽 셀만 그리므로, 왼쪽 셀의 매치까지 세면 번호가
어긋나 Enter를 눌러도 아무 데로도 가지 않는다. 그래서 `items`가 지금 보기 방식을 보고
그려지지 않는 셀은 세지 않는다. 같은 이유로 변경 위치 눈금도 실제로 그리는 목록
(`renderItems`)을 기준으로 센다.

펼치는 규칙(`web/src/inline.js`)은 순수 함수로 빼고 테스트로 고정했다. 특히 블록 번호를
펼친 **첫 줄에만** 남기는 것 — 두 줄에 붙으면 "다음 변경으로" 이동이 같은 자리를 두 번
세고 눈금도 겹쳐 찍힌다.

한편 바가 좁아지면 개수 표시(`N differences`) → 상태 배지 순으로 접는다. 컨테이너 질의
(`container-type: inline-size`)를 쓰는 이유는 이 패널의 폭이 뷰포트 폭과 다르기
때문이다 — 좌측 목록이 300px을 먹는다.

### 텍스트 선택을 한쪽 컬럼에 붙잡아 둔다

(한 줄 보기에는 컬럼이 하나라 이 문제가 없다. 격리 규칙을 `.scroll.split`으로 묶어 둔
이유가 그것이다 — 안 묶으면 `+` 줄에서 드래그를 시작한 순간 `−` 줄이 선택되지 않는다.)

side-by-side diff의 DOM 순서는 `[좌번호, 좌코드, 우번호, 우코드]`다. 그래서 선택이
행을 넘어가는 순간 반대쪽 셀을 지나간다 — 화면에서도 양쪽이 칠해지고, 복사하면
좌우가 뒤섞인 텍스트가 나온다. CSS만으로는 막을 수 없다.

드래그를 시작한 쪽을 기억하고(`mousedown`) **반대쪽 셀에 `user-select: none`을
준다.** 브라우저가 선택을 확장할 때 그 셀들을 건너뛰므로 한쪽 컬럼만 잡힌다.
줄 번호도 `user-select: none`이라 복사에 섞이지 않는다.

컬럼을 두 개의 독립 스크롤 영역으로 쪼개는 방법도 있지만, 그러면 좌우 스크롤을
직접 맞춰야 하고 행 높이가 어긋날 때마다 틀어진다. 지금 구조가 훨씬 단순하다.

### 코멘트는 여러 줄 범위를 받는다

한 줄만 받으면 "이 블록 전체를 왜 이렇게 바꿨어?"를 물을 수 없다. 줄 번호를 끌어
범위를 고르면 그 범위의 코드를 모아 저장하고, 프롬프트에는 `path:3-6`으로 적는다.

입력창은 **범위의 마지막 줄 아래**에 붙인다. 위에 붙이면 고른 범위를 가린다.

### 코멘트는 클립보드로 넘긴다

리뷰 흐름은 이렇게 끊겨 있었다: 브라우저에서 diff를 보고 → 머릿속에 기억 →
터미널로 가서 경로와 줄 번호를 다시 타이핑. 그 옮겨 적는 일을 없애는 것이 이
기능의 전부다.

**전달 수단은 클립보드다.** 저장소에 `review.md` 같은 파일을 떨어뜨리면 그것이
다시 변경 목록에 떠서 리뷰를 방해하고, AI 도구마다 파일을 읽는 방식도 다르다.
클립보드는 어떤 도구를 쓰든 붙여넣기가 되고 흔적을 남기지 않는다.

프롬프트에 담는 정보는 셋이다 — **경로 · 줄 번호 · 그때 본 코드**. AI가 위치를
정확히 찾는 데 필요한 최소치이고, `code`를 코멘트와 함께 저장해 두므로 그 사이
파일이 바뀌어도 무엇을 보고 쓴 코멘트인지 남는다. 형식은 `buildPrompt()` 순수
함수에 있고 테스트로 고정했다 — 이 문자열이 실제 산출물이다.

### 브랜치 이름은 `branch --show-current` 로 읽는다

`rev-parse --abbrev-ref HEAD` 를 쓰면 안 된다. 그 경로(`shorten_unambiguous_ref`)는 이름을
**29바이트에서 자른다.** ASCII 브랜치는 티가 안 나지만 한글 브랜치는 글자 중간이 잘려
깨진 문자로 끝난다 — 실제 저장소에서 발견했다 (Apple Git 2.39.5):

```
feature/GRMWEB3-1639-다인-접속-메모리-누수-개선
→ feature/GRMWEB3-1639-다인-<0xEC>      (rev-parse --abbrev-ref)
→ feature/GRMWEB3-1639-다인-접속-메모리-누수-개선  (branch --show-current)
```

`--show-current` 는 git 2.22부터라, 없으면 옛 경로로 떨어지고 detached 면 짧은 해시를 쓴다.

### 심볼릭 링크를 "바이너리"라고 하지 않는다

줄 수를 셀 수 없다고 전부 바이너리는 아니다. worktree 안에 도구가 만든
`.claude -> ../.claude` 같은 링크가 있으면 변경 목록에 매번 뜨는데, "바이너리 파일"로
보이면 정체를 알 수 없다. `git diff --numstat` 이 셀 수 없다고 답하면 `lstat` 으로 링크인지
확인해 **가리키는 곳**을 함께 준다. 목록에는 `링크`, 뷰어에는 `심볼릭 링크입니다 → ../.claude`.

### 요약을 지어내지 않는다

파일이 40개면 "지금까지 뭐가 됐지"를 다시 훑는 데 리뷰만큼 걸린다. 그래서 사이클
요약을 만들었는데, 여기서 하지 않기로 한 것이 더 중요하다: **코드가 무엇을 하는지는
적지 않는다.** 그걸 말하려면 모델이 필요하고, 그건 터미널의 AI가 이미 한다. 이 도구가
어설프게 요약하면 AI가 아는 것을 다시 말하면서 틀릴 여지만 만든다.

대신 **AI가 알 수 없는 것**을 모은다 — 사람이 무엇을 확인했고, 무엇이 아직 남았고,
어떤 코멘트가 아직 반영되지 않았고, 어디에 위험 신호가 붙었는지. git에도 없고 AI의
문맥에도 없다. 그래서 이 요약은 `git diff --stat`과 겹치지 않는다.

코멘트 원문은 줄이지 않고 그대로 옮긴다(줄바꿈만 편다). 줄여서 뜻이 바뀌면 그것이
곧 잘못된 지시가 된다.

### 컨텍스트는 담을 때가 아니라 넘길 때 읽는다

"이 파일도 같이 봐"를 하려고 사람이 터미널에 경로를 손으로 쳤다. 그래서 바구니를
만들었다. 여기서 정한 것 하나: **바구니는 내용을 들고 있지 않는다.** "무엇을 볼지"만
들고 있고, 프롬프트를 만드는 순간의 파일에서 내용을 읽는다.

담을 때 내용을 얼려 두면 AI가 고친 뒤에 넘긴 프롬프트가 사실과 달라진다. 이 도구는
AI가 계속 고치는 동안 쓰는 물건이라, 그 시차가 곧 잘못된 지시가 된다. 같은 이유로
검색어는 결과가 아니라 **검색어 자체**를 담고 넘길 때 다시 검색한다.

리뷰 코멘트는 반대다 — 거기 저장된 `code`는 "내가 그때 보고 쓴 것"이라는 증거라서
얼려 두는 게 맞다. 두 기능이 같은 파일에 살지만 시간에 대한 태도가 정반대다.

담는 자리는 셋이고, 모두 **이미 그 대상을 보고 있는 자리**다: diff 바의 `담기`(이
파일), 줄을 끌어 고른 뒤의 `구간 담기`, 검색 결과의 `⌥Enter`. 검색 결과에서 한
줄만 담지 않고 그 파일을 담는 이유는 한 줄로는 AI가 앞뒤를 볼 수 없기 때문이다.

600줄을 넘는 파일은 자르고 **잘랐다고 프롬프트에 적는다.** 감추면 AI가 "여기 없다"를
근거로 잘못 판단한다.

### 코멘트가 반영됐는지는 코드 조각으로 판정한다

리뷰를 AI에게 넘기고 나면 다음 질문은 늘 "저거 고쳐졌나"다. 코멘트가 쌓이기만 하면
리뷰가 한 방향으로 끝나고, 다음 사이클에는 이미 처리된 것까지 다시 보내게 된다.

판정 근거는 **코멘트를 달 때 함께 저장해 둔 코드 조각**이다. 줄 번호로 보지 않는
이유는 위쪽이 몇 줄만 바뀌어도 번호가 밀려 엉뚱한 줄을 보게 되기 때문이다. 조각은
밀려도 따라간다(테스트로 고정해 두었다).

방향은 어느 쪽에 단 코멘트냐로 뒤집힌다. 오른쪽(지금 코드)에 달았으면 **그 코드가
사라졌을 때** 반영이고, 왼쪽(삭제된 코드)에 달았으면 **되살아났을 때** 반영이다.

판정은 어림짐작이라고 화면에서도 말한다. AI가 코드를 그대로 두고 "확인했고 문제
없다"고 답한 경우는 알 수 없다. 그래서 자동으로 지우지 않고 `반영된 N개 정리`를
사람이 누른다. 커밋에 단 코멘트는 대상이 굳어 있어 판정 자체를 하지 않는다.

### 클립보드 복사는 클릭 핸들러 안에서 아무것도 기다리면 안 된다

골라 보내기를 만들면서 "고른 id로 프롬프트를 받아 온 다음 클립보드에 담기"로 짰다.
복사가 조용히 실패했다. 브라우저는 `await` 하나만 지나도 사용자 제스처가 끝난 것으로
보고 클립보드 권한을 회수한다 — `navigator.clipboard.writeText`가 거부되고,
`document.execCommand('copy')` 대체 경로도 같은 이유로 실패한다.

그래서 **선택이 바뀔 때 프롬프트를 미리 받아 둔다.** 버튼을 누르는 시점에는 이미
문장이 손에 있고, 핸들러는 담기만 한다. 이 규칙을 세 곳(코멘트·컨텍스트·요약)에서
쓰게 되어 담는 일 자체는 `web/src/lib/clipboard.js` 한 곳에 두었다. 프롬프트 문장을 서버가 만드는 규칙은 그대로
둔다 — 형식(파일별 묶기, `path:3-6` 표기, 코드 펜스)이 두 곳에 있으면 어긋난다.

### 위험 신호는 "조용히 사라진 것"을 먼저 본다

리뷰에서 위험한 것은 새로 들어온 코드보다 **사라진 것**이다. 추가된 줄은 눈에 띄지만
지워진 테스트나 없어진 에러 처리는 44개 파일을 훑는 동안 그냥 지나간다.

판정을 내리지 않는다. 린터가 아니라 "여기 한 번 보라"는 표시이므로 개수와 예시만
보여주고 사람이 판단한다. 틀릴 수 있다는 전제이므로 잡음을 줄이는 데 신경 썼다:

- 에러 처리는 **추가된 쪽에 같은 모양이 있으면 옮긴 것으로 보고** 그만큼 뺀다
- `describe`/`it`은 테스트 파일에서만 센다. 일반 코드에서는 다른 뜻일 수 있다
- 디버그 출력은 테스트 파일에서 세지 않는다 — 테스트에 남은 출력은 위험이 아니고,
  디버그 출력을 검사하는 테스트가 걸려 잡음이 된다(이 저장소에서 실제로 겪었다)
- 삭제가 커도 추가가 비슷하면 옮긴 것이므로 세지 않는다

**git 호출은 한 번이다.** 파일마다 diff를 돌리면 44개 파일에 44번 프로세스를 띄운다.
기준점이 쓰는 임시 index를 재사용해 `add -A` → `diff HEAD --cached -U0` 로 전체를
한 번에 받는다. 추적되지 않은 새 파일도 함께 들어오는 것이 부수 효과로 얻어진다.

### 확인 표시도 서버에 둔다

브라우저 localStorage에 두었더니 grmide가 다른 포트로 뜰 때(4317이 사용 중일 때)
다른 origin이 되어 **진행률이 통째로 사라졌다.** 저장소에 붙은 상태이므로 코멘트와
같은 파일에 둔다. 예전에 브라우저에 남아 있던 표시는 서버가 비어 있을 때 한 번
옮겨 온다.

### 코멘트 저장은 `.git` 안에

세 가지 이유로 워킹트리를 쓰지 않는다. 파일을 만들면 grmide 자신의 변경 목록에
뜬다. 저장소마다 따로 남아야 한다. 감시자가 `.git`을 보지 않으므로 저장할 때
화면이 새로고침되지 않는다.

브라우저 localStorage도 아니다 — 포트가 바뀌면 다른 origin이 되어 내용을 잃는다.
(확인 체크는 아직 localStorage에 있고, 같은 이유로 옮겨야 한다. 로드맵 항목.)

쓰기는 임시 파일에 쓴 뒤 rename한다. 쓰다 죽어도 반쪽 JSON이 남지 않는다.

### 문서 탭이 무엇을 보여줄지 정한다

⌘P로 아무 파일이나 열 수 있게 되자 "한 번에 하나만 본다"는 구조가 무너졌다. 그래서
`useTabs`가 열어 둔 문서 목록을 들고, 뷰어는 **활성 탭 하나**를 그린다. 좌측 목록의
선택은 이제 "탭을 연다"는 뜻이다.

탭 종류가 셋(`worktree` · `commit` · `file`)이고 갱신 규칙이 다르다:

- 워킹트리 탭만 SSE 알림에 낡은 것으로 표시한다. 커밋과 파일 내용은 확정된 것이라
  다시 받을 이유가 없다.
- 낡은 표시는 해 두되 **그 탭을 실제로 볼 때 다시 받는다.** 탭 열 개를 열어 둔
  상태에서 파일이 하나 바뀔 때마다 열 번 요청할 이유가 없다.
- 받아 둔 데이터는 탭에 담는다. 탭을 오가는 것이 매번 요청이면 탭의 의미가 없다.
- 목록에서 사라진 워킹트리 탭은 닫는다(커밋/되돌림). 없는 파일의 diff를 띄워 둘 수 없다.
- 12개를 넘으면 가장 오래 안 본 탭을 버린다. 현재 탭은 버리지 않는다.

닫기 단축키는 `⌥W`, 이동은 `⌥←/→`, 되살리기는 `⌥⇧T`다. `⌘W`·`⌘⇧T`·`⌘⇧[ ]`는 브라우저가
먼저 가져간다 — 웹 앱이라서 생기는 제약이고, 여기서 다툴 이유가 없다. 그래서 탭 관련
단축키는 모두 `⌥` 쪽에 모았다.

**`⌥` + 글자는 `event.key`가 아니라 `event.code`로 봐야 한다.** macOS에서 `⌥`를 누르면
OS가 글자를 바꿔 보낸다 — `⌥W`는 `key: '∑'`, `⌥T`는 `key: '†'`다. 원래 `⌥W` 처리가
`key.toLowerCase() === 'w'` 였는데 실제 키보드에서 맞지 않았다. `code`는 자리 이름
(`KeyW`)이라 배열·조합에 흔들리지 않는다. (합성 이벤트로 테스트하면 `key`가 채워져
나와서 이 문제가 안 보인다 — 실제 키로 확인해야 한다.)

### 한 번 누르면 대신하고, 두 번 누르면 붙잡는다 (2026-07-28)

목록에서 파일을 고를 때마다 탭이 쌓였다. 훑어보기만 해도 12개가 금방 차고, 그러면
`evict`가 정작 붙잡아 두려던 탭을 버린다. 고른다는 것이 곧 "영구히 연다"는 뜻이면
목록을 마음 놓고 훑을 수 없다.

그래서 **미리 보기 탭을 하나 둔다**(`preview: true`). 한 번 누르면 그 자리를 *대신하고*,
두 번 누르면 *붙잡는다*. VS Code와 같은 규칙이라 설명이 필요 없다는 것도 이유다.

- **`click` 다음 `dblclick`이 오는 순서에 기댄다.** 한 번 누르는 것이 이미 미리 보기로
  열어 두었으므로, 두 번 누르기는 그 탭을 붙잡기만 하면 된다. 두 이벤트를 조율하는
  코드(타이머로 click을 미루는 식)를 만들지 않아도 된다.
- **미리 보기는 있던 자리를 물려받는다.** 뒤에 새로 붙이면 방금 누른 것을 눈으로 다시
  찾아야 한다.
- **기울임으로 표시한다.** 다음에 무엇을 고르면 이 자리가 없어지는지가 보여야 한다.
  색이나 투명도로 구분하면 "안 읽은 것"이나 "낡은 것"처럼 읽힌다.
- **미리 보기는 "훑는 동작"에만 쓴다.** 목록에서 한 번 누르기와 `j`/`k`가 그것이다.
  `⌘P`·검색 결과·시트에서 여는 것은 이미 무엇을 볼지 정하고 찾아온 것이라 곧바로
  붙잡는다 — 다음에 무엇을 누르면 사라지는 탭으로 주면 오히려 놀란다. (처음에는 이쪽도
  미리 보기로 뒀는데 써 보니 어긋났다.)
- 문서 안 링크만 예외로 미리 보기다. 읽던 흐름을 따라가는 것이라 문서를 몇 개 거치면
  탭이 쌓인다.

**되살리기(`⌥⇧T`)는 사람이 닫은 것만 대상으로 한다.**

- 미리 보기를 닫은 것은 남기지 않는다. 붙잡지도 않은 것을 되살리면 목록이 금방
  지저분해진다.
- `evict`로 밀려난 것과 `pruneWorktree`로 사라진 것도 남기지 않는다. 앞은 사람이 닫은
  것이 아니고, 뒤는 그 변경 자체가 이제 없다.
- 데이터(diff 내용)는 버리고 무엇을 보고 있었는지만 남긴다. 되살릴 때 다시 받으면 되고,
  그 사이에 워킹트리가 바뀌었을 수도 있다.
- 자리도 기억한다. 닫은 것을 다시 열면 있던 자리에 있길 기대한다.
- 되살린 탭은 붙잡은 상태로 둔다. 일부러 다시 열었는데 또 밀려나면 안 된다.

### 확인 시점 — 파일마다 "내가 읽은 뒤"가 다르다 (2026-07-28)

기준점(baseline)은 워킹트리 **전체**를 한 순간에 굳힌다. 사람이 직접 잡아야 하고, 잡은
뒤에는 파일 40개가 한꺼번에 "기준점 이후"가 된다.

실제로 AI와 오갈 때는 파일마다 본 시점이 다르다. A를 읽고, AI가 A와 B를 고치고, B를 읽고,
AI가 다시 A를 고친다. 이때 알고 싶은 것은 "A에서 **내가 읽은 뒤** 무엇이 더 바뀌었나"다.
목록의 점(`fresh`)은 *어느 파일*인지는 알려줬지만 *무엇이* 바뀌었는지는 말해 주지 않았다 —
그걸 보려면 HEAD 대비 전체 diff를 다시 훑어야 했고, 그게 이 도구가 없애려던 일이다.

그래서 **파일별로 누적되는 트리**를 하나 둔다(`refs/grmide/seen`). 기준점과 같은 재료를
쓰지만 갱신 방식이 다르다: `확인`을 누른 파일만 그때 내용으로 갈아 넣는다. 앞서 쌓아 둔
트리를 임시 index로 불러온 뒤 그 경로만 바꿔 다시 `write-tree` 한다.

- **트리거는 `확인`이다.** 탭을 열었다고 자동으로 옮기면 스크롤도 안 한 변경까지 "봤다"가
  되어 조용히 삼켜진다. 이 도구는 이미 `확인`을 "봤다"의 뜻으로 쓰고 있다(진행률 N/M).
- **표시를 풀어도 스냅샷은 남긴다.** 그 기록은 "마지막으로 확인했을 때 내용이 이랬다"는
  사실이고, 표시를 껐다고 없던 일이 되지 않는다. 지문이 바뀌어 확인이 자동으로 풀린
  경우에도 그대로다 — 그래야 "확인 이후 무엇이 바뀌었나"에 답할 수 있다.
- **기준점과 index 파일을 나눠 쓴다.** 같은 파일을 쓰면 `add -A`가 훑어 둔 stat 캐시를
  서로 무너뜨려 매번 저장소 전체를 다시 해시한다.
- `--add --remove`를 함께 준다. 확인한 뒤 파일이 지워지는 경우도 기록해야 하고, `--add`만
  주면 없는 파일에서 실패한다.
- 추적되지 않은 파일도 들어간다. AI가 방금 만든 파일이 가장 자주 보는 것이라 여기서 빠지면
  쓸모가 없다.

**스냅샷이 없으면 `seenFileDiff`는 `null`을 돌려준다.** 빈 문자열이 아니다 — 빈 문자열은
"바뀐 것이 없다"이고, 스냅샷이 없는 것은 "이 질문에 답할 수 없다"라서 부르는 쪽이 다르게
처리해야 한다. 그대로 diff를 뜨면 파일 전체가 새로 추가된 것처럼 나온다. 화면도
`/api/status`의 `seen` 플래그로 선택지를 감추지만, 상태가 낡은 사이에 요청이 올 수 있어
서버도 HEAD 대비로 떨어뜨리고 **무엇으로 떴는지 응답에 담는다**(`compare`). 화면이 고른
것과 실제가 어긋날 수 있기 때문이다.

`base=1` 불리언을 `compare=head|baseline|seen`으로 바꿨다. 서로 배타적인 불리언 두 개를
두면 "둘 다 1이면?"이 생긴다. 옛 `base=1`은 한 번 더 받아 준다.

한 가지 함정을 실제로 밟았다. 확인 표시 저장은 200ms 디바운스인데, `전체 확인`이 저장을
걸어 놓고 곧바로 `/api/status`를 다시 받아서 **PUT보다 앞질러 낡은 `seen` 플래그를 읽었다.**
그래서 방금 확인한 파일에 '확인 이후'가 뜨지 않았다. 저장이 끝난 뒤 상태를 다시 받도록
`useReview`에 `onSaved`를 뒀다. 정리(`prune`)는 그 갱신 안에서 다시 일어나므로 알리지
않는다 — 갱신 → 정리 → 갱신으로 되돌아온다.

이 기능은 전부 git 플럼빙이라 순수 함수 테스트로는 잡히지 않는다. 틀렸을 때의 증상도
"diff가 조금 이상하다"라서 눈으로는 놓친다. 그래서 임시 저장소를 만드는 첫 통합 테스트를
`test/seen.test.js`에 뒀다.

### 마크다운은 HTML이 아니라 트리로 그린다 (2026-07-28)

문서도 "눈으로 봐야 판단이 되는" 파일이다. diff로 보면 `## 제목`과 `| a | b |`가 글자로
남는데, 문서를 검토할 때 정작 필요한 것이 그 모양이다. 그걸 보려고 GitHub나 IDE를 켜면
이 도구의 존재 이유가 사라진다.

**`marked` 같은 라이브러리를 쓰지 않았다.** 그것들은 HTML 문자열을 내놓으므로 `v-html`로
심어야 하고, 그 순간 저장소 파일 내용이 그대로 DOM 스크립트가 된다. 막으려면 `DOMPurify`
같은 살균기를 또 붙이고 그 설정이 맞는지를 계속 믿어야 한다.

대신 파서가 **블록 트리**를 내놓고 Vue가 요소로 그린다. `v-html`이 한 줄도 없으므로
`<script>`는 텍스트 노드가 된다 — 막는 코드가 아니라 구조가 막는다. 이 저장소가 diff
파서와 토크나이저를 직접 가진 방식과도 같고, 순수 함수라 `test/markdown.test.js`로
검증된다.

남는 위험은 **주소 하나**다. 태그는 주입되지 않지만 `href`는 우리가 넣는 값이라
`[클릭](javascript:alert(1))`이 살아난다. 그래서 `safeHref`가 스킴을 화이트리스트로
검사한다. 통과하지 못하면 링크를 버리고 **글자로 남긴다** — 조용히 지우면 문서에서
내용이 사라진 것처럼 보인다.

목표는 CommonMark 완전 구현이 아니다. 개발 문서에 실제로 쓰이는 문법만 다루고, **이
저장소의 `docs/`가 시험지다** — 테스트가 6개 문서를 파싱해 원문의 낱말과 링크 주소가
하나도 사라지지 않았는지 확인한다. 문단이 통째로 코드 블록에 삼켜지는 종류의 사고는
단위 테스트로는 안 잡히고 실제 문서로만 잡힌다.

곁들여 정한 것:

- **기본값이 모드에 따라 다르다.** ⌘P로 문서를 *읽으려고* 열었으면 그려진 쪽이 맞고,
  변경 목록에서 골랐다면 알고 싶은 것은 "AI가 문서를 어떻게 바꿨나"라서 diff가 맞다.
  그림은 이 갈림이 없어서(png는 diff가 아예 없다) 지금까지 상수로 둘 수 있었다.
- **원문은 `/api/blob`으로 받는다.** diff 행을 이어붙이면 "변경 부분"만 받아 온 상태에서
  문서 절반이 비어 이상한 문서가 그려진다. 어느 버전을 볼지 정하는 규칙도 한 곳에만
  있어야 화면과 어긋나지 않는다.
- **저장소 안의 그림만 불러온다.** 바깥 주소는 alt와 함께 표시만 한다. 문서를 열었다는
  사실이 그 서버에 새어 나가고, 이 도구는 "git이 보는 세계"에 머물기로 했다.
- **문서 간 링크는 이 도구의 탭으로 연다.** 문서들이 서로를 참조하는데 링크가 죽으면
  읽다가 ⌘P로 돌아가야 하고, 그게 없애려던 번거로움이다. 상대 경로는 문서 위치를 기준으로
  풀고(`docs/ROADMAP.md` + `ARCHITECTURE.md` → `docs/ARCHITECTURE.md`), `..`가 저장소
  밖으로 나가면 링크로 만들지 않는다.
- **코드 펜스는 diff와 같은 강조기·같은 밀도를 쓴다.** 마크다운 전용 강조를 따로 만들면
  java 펜스가 뷰어에서 보던 색과 달라지고, ⌘+/⌘-도 문서 안에서만 안 듣게 된다.
  이때 `.tk-*` 클래스를 `DiffViewer`의 scoped 스타일에서 `style.css`로 옮겼다 — 두 곳이
  같은 표를 베끼면 `--tok-*` 토큰과 클래스 이름의 짝이 갈라진다.
- **맨 URL 을 자동으로 링크한다(GFM).** README 의 GitHub 첨부 영상이 그 형태다 —
  마크다운으로 감싸면 GitHub 이 플레이어로 바꿔 주지 않아 맨 URL 로 둬야 하고, 그러면
  미리보기에서 누를 수 없는 긴 문자열이 된다. 문장 끝 마침표와 감싼 괄호는 떼고,
  주소 안의 짝맞는 괄호는 남긴다(위키 주소).
- **체크 항목(`- [x]`)을 그린다.** ROADMAP이 온통 그 문법이라 글자로 남기면 미리보기가
  원문보다 읽기 어려워진다. 누를 수는 없다 — 읽기 전용이고, 상태를 바꾸는 일은 AI에게
  시킨다.
- **산문에는 밀도 원칙을 적용하지 않는다.** 폭을 72em으로 제한하고 줄 높이를 1.72로 둔다.
  코드 영역의 규칙(한 화면에 많이)은 diff를 위한 것이고, 산문은 여백이 있어야 읽힌다.

### 긴 문서에서 절로 가는 길 (2026-07-28)

785줄짜리 `ARCHITECTURE.md`를 그려 놓고 원하는 절로 갈 방법이 없으면 그린 값이 반감한다.
문서를 그리는 것까지 해 놓고 그 안에서 길을 잃는 셈이다.

- **제목마다 앵커 id를 붙인다.** 규칙은 GitHub와 똑같이 맞췄다(`## 설계 결정` →
  `#설계-결정`) — 규칙을 새로 만들면 문서에 **이미 적혀 있는** 링크가 전부 죽는다.
  한글은 그대로 남기고, 문장부호만 버린다. 같은 이름의 절은 뒤에 `-1`을 붙인다.
- 앵커는 파서가 붙인다. 중복 판정이 문서 전체에 걸쳐 있어야 하고(인용·목록 안의 제목까지),
  그 정보를 가진 곳이 파서다. 그래서 `slugify`·`tableOfContents`도 순수 함수로 테스트된다.
- GitHub에서 복사한 링크는 한글이 퍼센트 인코딩돼 있다. `decodeURIComponent`로 되돌린다.
- **`목차`는 토글이고 선택을 기억한다.** 이 도구는 터미널 옆 좁은 폭에서 뜨므로 목차가 항상
  자리를 차지하면 안 된다. 제목이 셋 아래면 버튼도 내놓지 않는다. 패널 폭이 400px 아래로
  좁아지면 컨테이너 질의로 스스로 숨는다 — 창 크기가 아니라 **패널 폭**이 기준이다.
- 지금 읽는 절은 `IntersectionObserver`가 아니라 스크롤 위치로 센다. 제목이 화면에 여러 개
  보일 때 "지금 절"은 교차 여부가 아니라 **위에서 가장 가까운 제목**이라서다.

**`scrollIntoView`를 쓰지 않는다.** 이걸로 만들었더니 `.main`이 38px 밀려 탭 바가 화면 밖으로
나갔다(측정으로 확인). 브라우저가 요청 조건을 맞추려고 바깥 컨테이너까지 함께 밀기 때문이고,
`style.css`가 `overflow: hidden`으로 막아 둔 것과 같은 사고다. 목표 위치를 직접 계산해
그 영역의 `scrollTop`만 건드리면 다른 데가 움직이지 않는다.

문서에 적힌 앵커가 실제 제목과 맞는지는 테스트가 확인한다. 이게 어긋나면 **링크는 눌리는데
아무 일도 일어나지 않는다** — 가장 알아채기 어려운 고장이라 사람 눈에 맡길 수 없다. 지금
저장소 문서에서 10개를 검사한다.

### 파일 뷰어는 DiffViewer의 한 컬럼 모드다

⌘P로 파일을 열면 별도 컴포넌트가 아니라 `DiffViewer`에 `single` 플래그를 준다.
내용을 `{type:'context', right:{num,text}}` 행으로 바꿔 넘기면 문법 강조, 찾기(⌘F),
줄바꿈 토글, 스크롤 처리가 그대로 따라온다.

별도 `FileViewer`를 만들다가 접었다. 같은 것을 두 번 만들면 ⌘F 같은 기능을 두
곳에 넣어야 하고, 한쪽만 고치는 일이 반드시 생긴다.

### 찾기 강조는 토큰 계산과 분리한다

`buildSpans`는 세 계층(문법 토큰 · 변경 구간 · 찾기 결과)을 합친다. 하지만
토크나이즈는 파일이 바뀔 때만(`baseItems`), 찾기 강조는 검색어가 바뀔 때만(`items`)
계산한다.

한 computed에 다 넣으면 검색어를 한 글자 칠 때마다 파일 전체를 다시 토크나이즈한다.
파일 전체 보기에서 수천 줄이면 타이핑이 눈에 보이게 밀린다.

### 검색 결과에는 그래프를 그리지 않는다

검색으로 걸러낸 목록은 부모가 대부분 빠져 있어 위상이 끊긴다. 그 상태로 레인을
계산하면 커밋마다 새 레인을 잡아 **그래프 폭이 커밋 수만큼 늘어나고**, 그려진 선도
사실과 다르다. 그래서 `filtered`일 때는 `flatLanes()`로 점만 찍고, 화면에도 왜 선이
없는지 한 줄로 알린다.

거짓 그림을 그리는 것보다 안 그리는 쪽이 낫다는 판단이다. 테스트로 두 함수의 차이를
고정해 뒀다(끊긴 20개 목록 → `computeLanes`는 레인 폭이 터지고 `flatLanes`는 1).

### ref는 존재 확인까지 하고, 검색어는 인자 하나에 갇힌다

둘 다 사용자 입력이 git 명령에 들어가지만 위험도가 다르다.

- **검색어**는 `--grep=<q>`, `-S<q>` 처럼 인자 **하나 안에** 들어간다. 셸을 거치지
  않으므로 `-`로 시작해도 옵션으로 해석되지 않는다. 길이만 자른다(200자).
- **ref**는 리비전 자리에 그대로 놓인다. `--all`이나 `-S...`가 오면 옵션이 된다.
  그래서 `-`로 시작하면 거부하고, `rev-parse --verify <name>^{commit}`로 실제
  존재하는지 확인한다. 통과하지 못하면 오류로 만들지 않고 무시하고 전체를 보여준다 —
  브랜치를 지운 뒤 새로고침한 경우가 오류 화면이 될 이유는 없다.

### 히스토리는 기본으로 모든 브랜치를 본다

`git log`처럼 HEAD 조상만 보여주면 다른 브랜치가 통째로 사라진다. 브랜치 그림을
보려고 이 화면을 여는 사람에게는 그게 쓸모없다. 그래서 `--all`이 기본이고,
`현재 브랜치`로 좁히는 토글을 둔다.

### 병합 커밋은 첫 부모와 비교한다

combined diff(`git show`의 기본)는 읽기 어렵다. `<sha>^1 <sha>` 비교가 "이 머지가
무엇을 들여왔나"를 보여주는 실용적인 답이고, IDE들도 그렇게 한다.

### 더 보기로 이어 받은 구간의 레인은 다시 계산하지 않는다

레인은 받아온 구간 안에서만 계산되므로, 페이지를 이어 붙이면 경계에서 선이 살짝
어긋날 수 있다. 전체를 다시 받아 계산하면 정확하지만 비용이 크다. 경계 한 줄의
모양이 어긋나는 정도는 감당할 수 있다고 판단했다.

### 터미널에도 요약을 찍는다

주소만 찍고 끝내면 "브라우저를 봐야 뭐가 바뀐지 안다"가 된다. 이 도구를 쓰는
사람은 터미널에 손을 두고 있으니, 브라우저를 열기 전에 규모를 알 수 있어야 한다.
변경이 없으면 열 필요조차 없다는 것도 그 자리에서 알게 된다.

정렬은 글자 수가 아니라 **표시 폭**으로 계산한다. `경로`·`변경` 같은 한글 라벨은
터미널에서 두 칸씩 차지해서, `padEnd`로 맞추면 `HEAD` 줄과 어긋난다.

색은 `process.stdout.isTTY`일 때만 넣고 `NO_COLOR`를 존중한다. 로그로 리다이렉트한
출력에 escape 코드가 섞이면 안 된다. 덕분에 테스트에서도 평문으로 검사할 수 있다.

요약을 만들다 실패해도 주소는 반드시 출력한다. 부가 정보 때문에 본래 기능을
못 쓰게 되면 안 된다.

### 파일 전체 보기와 변경 위치 눈금

보기 범위는 `git diff -U<n>`의 n을 바꾸는 것으로 구현한다. "파일 전체"는
`-U100000`이며, 어떤 파일이든 전체가 한 훅으로 온다. 클라이언트에 따로 파일
내용을 받아오는 경로를 만들지 않아도 되고, 변경 표시 로직이 그대로 재사용된다.

전체를 보여주기만 하면 변경된 곳이 긴 내용 사이에 묻힌다. 그래서 오른쪽에 변경
블록 위치를 눈금으로 찍는다. 위치는 행 인덱스 비율로 잡는다 — 모든 행 높이가
같아서 스크롤 비율과 거의 일치하고, 실제 이동은 `scrollIntoView`가 정확히 한다.

눈금은 스크롤 영역에 겹치지 않고 나란히 둔다(12px). 코드 위에 얹으면 글자를 가린다.

보기 범위는 `localStorage`에 저장한다. 파일마다 다시 고르게 하면 쓸 수 없다.

### scrollIntoView에 behavior: 'smooth'를 쓰지 않는다

중첩 스크롤 컨테이너에서 `behavior: 'smooth'`가 **아무 일도 하지 않는 경우가 있다.**
측정으로 확인했다: 같은 요소에 대해 smooth는 0px, 기본값(즉시)은 415px 이동.

이 때문에 변경 사이 이동(`↑` `↓`)이 한동안 조용히 동작하지 않았다. 카운터만
올라가고 화면은 그대로였다. 변경 사이 점프는 어차피 즉시 이동이 낫다.

### 확인 상태에 변경 지문을 함께 저장한다

경로만 기록하면 그 파일이 다시 바뀌었을 때도 "확인함"으로 남는다. AI가 계속
고치는 상황에서는 이게 오히려 위험하다. `status:추가줄수:삭제줄수`를 지문으로
저장하고 지문이 달라지면 확인 상태를 자동으로 해제한다.

저장 위치는 `localStorage`의 `grmide:reviewed:<저장소 절대경로>`. 서버에
두지 않는 이유는 이 상태가 "그 사람이 어디까지 봤는지"라는 개인적/일시적
정보이고, 저장소를 오염시킬 이유가 없기 때문이다.

### 토큰 인증을 넣는다 (로컬인데도)

`127.0.0.1`에만 바인딩해도 같은 머신의 다른 프로세스와, 브라우저에서 열어둔
아무 웹사이트가 `http://127.0.0.1:4317`로 요청을 보낼 수 있다. 이 서버는 소스
코드 전체를 읽어주므로 토큰이 없으면 안 된다.

`EventSource`는 헤더를 붙일 수 없어 SSE만 쿼리 파라미터로 토큰을 받는다.
초기 진입 URL의 `?t=`는 `sessionStorage`로 옮긴 뒤 `history.replaceState`로
주소창에서 지운다 — 주소를 복사해 공유하는 사고를 막는다.

### git 호출은 항상 execFile

`exec`(셸 경유)를 쓰면 경로에 공백이나 `$`, `;`가 들어간 순간 문제가 된다.
사용자가 만든 브랜치명/파일명이 그대로 들어오는 자리이므로 인자 배열로만 넘긴다.

### 경로 검증을 서버에서 한다

`git diff -- <path>`는 저장소 밖 경로를 알아서 거부하지만, untracked 파일에
쓰는 `--no-index` 비교는 임의 경로를 읽는다. `path.resolve` 후 저장소 루트 밖이면
403으로 막는다.

### 한 프로세스가 한 저장소를 본다

여러 저장소를 탭으로 전환하는 구조가 더 편하지만, 초기 버전에서는 포트 충돌 시
다음 포트로 넘어가는 방식으로 여러 저장소를 동시에 띄운다. 데몬 통합은
[ROADMAP](ROADMAP.md) 항목으로 남겨 두었다.

## 알려진 한계

- **가상 스크롤이 없다.** 서버에서 20,000행까지만 보내고 잘라낸다 (`truncated`
  플래그로 화면에 알린다). 파일 하나가 그보다 크면 터미널에서 봐야 한다.
- **문법 강조가 줄 단위다.** 여러 줄 주석, 템플릿 리터럴, 여러 줄에 걸친
  JSX/템플릿 식은 가끔 틀리게 칠해진다. 지원 언어는 js/ts, vue, html, css/scss,
  json이고 나머지는 색 없이 나온다.
- **다크 테마만 있다.**
- **rename 표시가 약하다.** status에 `origPath`는 담기지만 화면에는 새 경로만
  보여준다.

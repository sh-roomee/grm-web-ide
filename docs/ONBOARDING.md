# grmide를 왜, 어떻게 쓰는가

처음 이 저장소를 받은 사람을 위한 문서. 5분이면 읽고, 10분이면 첫 사이클을 돌릴 수 있다.

---

## 1. 무엇이 달라졌나

AI로 개발하면 **사람이 하는 일이 바뀐다.**

| | 전 | 지금 |
| --- | --- | --- |
| 코드를 쓰는 주체 | 사람 | AI |
| 사람이 하는 일 | 타이핑·리팩토링·탐색 | **읽고 판단하고 지시하기** |
| 한 번에 오는 변경 | 내가 방금 쓴 몇 줄 | **파일 20~40개** |

IDE는 첫 번째 열을 위해 설계됐다. 편집기·리팩토링·디버거·인덱싱은 모두 "사람이 코드를
쓴다"는 전제에서 나온 기능이다. 그런데 지금 하루의 대부분은 **AI가 만든 변경을 읽는
데** 쓴다.

읽기용 도구가 없어서 생기는 구체적인 통증은 이렇다.

**1) 이미 본 것과 새로 바뀐 것이 구분되지 않는다.**
AI가 20분 동안 계속 고치는 동안 `git diff`는 매번 전체를 다시 보여준다. 40개를 훑고
나서 3개가 더 바뀌었는데, 그 3개가 어디인지 알 방법이 없다. git에는 `HEAD`와 index만
있고 **"내가 마지막으로 확인한 시점"이라는 개념이 없다.**

**2) 조용히 사라진 것을 놓친다.**
추가된 줄은 눈에 띈다. 지워진 테스트, 없어진 `try/catch`, 사라진 에러 처리는 파일
수십 개를 훑는 동안 그냥 지나간다.

**3) 리뷰 결과를 손으로 옮겨 적는다.**
브라우저에서 diff를 보고 → 머릿속에 기억 → 터미널로 가서 경로와 줄 번호를 다시 타이핑.
이걸 하루에 수십 번 한다.

grmide는 이 세 가지를 겨냥한다. **IDE를 대체하려는 것이 아니라, IDE를 켜는 이유를
없애려는 것이다.**

## 2. 5분 시작

```bash
git clone git@github.com:sh-roomee/grm-web-ide.git
cd grm-web-ide
npm install && npm run build && npm link
```

이제 **아무 git 저장소에서** 치면 된다.

```bash
cd ~/work/my-project
grmide
```

터미널에 규모가 먼저 뜨고 브라우저가 열린다.

```
grmide  my-project  ⎇ main
경로    /Users/me/work/my-project
HEAD    58f27b2 add locales and noiseCancel lib · 7 minutes ago
변경    4개 파일  +20 -11
        staged 1 · unstaged 2 · untracked 1

  M src/locales/ko.json         +9 -2 staged
  M src/components/Display.vue  +5 -7
  ? src/styles.scss             +3

주소    http://127.0.0.1:4317/?t=3f8a...
```

변경이 없으면 그렇게 알려준다 — **브라우저를 열 필요조차 없다는 걸 그 자리에서 안다.**

끝낼 때는 `Ctrl-C`. 브라우저 탭은 열어둔 채로도 종료된다.

> 하위 디렉토리에서 실행해도 저장소 루트를 스스로 찾는다. 여러 저장소를 동시에 띄우려면
> 각 디렉토리에서 그냥 `grmide`를 치면 된다(포트가 겹치면 다음 번호로 넘어간다).

## 3. AI와 한 사이클 돌리기

여기가 이 도구의 전부다. 아래 흐름이 몸에 익으면 나머지는 부수 기능이다.

### ① 시작 전에 기준점을 잡는다

브라우저 상단 **`전체 확인`** 을 누른다. 지금 워킹트리가 트리 객체로 굳어 "여기까지
봤다"는 표시가 된다.

> 왜 필요한가: 이 시점 이후 AI가 고친 파일만 골라내기 위해서다. 이게 없으면 매번
> 전체를 다시 봐야 한다.

### ② AI에게 작업을 지시한다

터미널에서 평소처럼 시킨다. grmide는 브라우저에 열어둔 채로 둔다 — **파일이 바뀌면
알아서 따라온다.** 새로 고칠 필요도, 창을 눌러 포커스를 줄 필요도 없다.

### ③ 새로 바뀐 것만 본다

AI가 멈추면 상단을 본다.

| 표시 | 뜻 | 누르면 |
| --- | --- | --- |
| **새 변경 3** | 기준점 이후 바뀌고 아직 확인 안 한 파일 | 그 파일만 보기 |
| **⚠ 2** | 놓치기 쉬운 지점이 있는 파일 | 그 파일만 보기 |

`⚠`부터 보는 편이 좋다. **삭제된 테스트 · 사라진 에러 처리 · 남은 `console.log` ·
의존성 변경 · 크게 지워진 파일**을 잡아준다. 린터가 아니라 "여기 한 번 보라"는 표시다.

### ④ 파일을 하나씩 확인해 넘긴다

파일을 열면 상단에 **`✓ 확인 · 남은 2`** 가 있다. 누르면 다음 새 변경으로 자동으로
넘어간다. `space` 키로도 된다. 파일 44개를 훑을 때 필요한 건 이 반복뿐이다.

diff가 헷갈리면 `기준점 대비`로 바꿔 본다 — **이미 확인한 변경은 회색 컨텍스트로
내려가고 새로 바뀐 것만 변경으로 뜬다.**

### ⑤ 고쳐야 할 것은 코멘트로 남긴다

줄 번호를 클릭하거나 **여러 줄을 끌어서** 코멘트를 단다(`⌘Enter` 저장). 삭제된 쪽에도
달 수 있어서 "이 줄은 왜 지웠어?"를 물을 수 있다.

### ⑥ 코멘트를 AI에게 넘긴다

상단 **`리뷰 3`** 을 누르면 코멘트가 파일별로 모인다. 보낼 것을 고르고
**`선택 N개 · 프롬프트 복사`** → 터미널에 붙여넣기. 이런 형태로 나온다.

````
아래 리뷰 코멘트를 반영해줘.

## src/api.js

### src/api.js:12-18
```js
    const res = await fetch(`/users/${id}`)
    return res.json()
```
에러 처리가 사라졌어. 원래 try/catch가 있었는데 왜 뺐어?
````

경로·줄 번호·**그때 본 코드**가 함께 들어가므로 AI가 위치를 정확히 찾는다. 손으로
옮겨 적는 일이 없어진다.

### ⑥.5 읽을 곳도 함께 넘긴다

"이 파일도 같이 봐"가 필요하면 **컨텍스트 바구니**에 담는다. diff 위 `담기`(이 파일),
줄을 끌어 고른 뒤 `구간 담기`, 검색 결과에서 `⌥Enter`. 상단 `컨텍스트 N`에서
`프롬프트 복사`로 넘긴다.

내용은 **넘길 때** 읽는다. 담아 둔 내용을 얼려 두면 AI가 고친 뒤에는 프롬프트가
사실과 달라진다.

### ⑦ 반영됐는지 되짚는다

AI가 고치고 나면 `리뷰 N` 옆에 **반영 M**이 뜬다. 코멘트를 쓸 때 함께 저장해 둔 코드
조각이 그 사이 바뀌었는지로 판정한 값이다. 스레드를 열면 처리된 것은 **반영됨**으로
빠져 있어서, 다음에 보낼 때 이미 한 일을 다시 보내지 않는다.

판정은 어림짐작이다 — AI가 코드를 그대로 두고 "확인했고 문제 없다"고 답한 경우는 알
수 없다. 그래서 지우는 것도 사람이 누른다(`반영된 N개 정리`).

### ⑧ ②로 돌아간다

다음 지시를 쓰기 전에 상단 `요약`을 누르면 이번 사이클이 한 장으로 나온다 — 확인한
것, 남은 것, 아직 반영 안 된 코멘트, 위험 신호. 붙여 넣고 "남은 것부터 처리해줘"로
이어가면 된다.

AI가 고치면 새 변경만 다시 뜬다. 마음에 들면 목록에서 `+`로 stage하고 터미널에서
커밋한다. 그리고 다시 `전체 확인`으로 기준점을 옮긴다.

## 4. 코드를 읽어야 할 때

리뷰 중에 "이 함수를 쓰는 다른 곳"을 봐야 하는 순간이 온다. 그때 IDE를 켜면 이 도구의
존재 이유가 사라지므로, **읽기는 넓게 지원한다.**

| 키 | 하는 일 |
| --- | --- |
| `Shift` `Shift` | 통합 검색 — 파일·커밋·텍스트를 한 번에 |
| `⌘P` | 파일 열기 (경로 퍼지 매칭: `dvue` → `web/src/components/DiffViewer.vue`) |
| `⌘⇧F` | 저장소 전체 텍스트 검색 (`git grep`) — 결과를 누르면 **그 줄로 이동** |
| `⌥Enter` | 검색 결과를 열지 않고 **컨텍스트에 담는다** |
| `⌘F` | 지금 보고 있는 파일에서 찾기 |
| `⌘+` `⌘-` | 코드 글자 크기 11–17px (`⌘0` 기본값). 브라우저 확대와 달리 **코드 영역만** 커진다 |
| `Tab` | 변경사항 ↔ 히스토리 |
| `⌥←` `⌥→` | 문서 탭 이동 (`⌥W` 닫기) |
| `j` / `k` | 다음/이전 파일 (히스토리에서는 커밋) |
| `space` | 이 파일 확인 |

파일은 **읽기 전용**으로 열린다. 문법 강조와 `⌘F`가 그대로 동작하고, 열어본 것은 탭으로
쌓인다. 검색은 추적되지 않은 파일도 본다 — AI가 방금 만든 파일이 빠지면 가장 자주 찾을
것을 못 찾는다.

히스토리 탭에서는 브랜치 그래프와 커밋별 diff를 본다. `git log --graph`의 ASCII가
브랜치 셋만 넘으면 읽을 수 없어서 만든 화면이다.

## 5. 기대하지 말아야 할 것

정직하게 적는다. 이걸 알고 쓰면 실망하지 않는다.

- **편집이 없다.** 코드를 쓰는 일은 터미널의 AI가 한다. 이건 절대적인 선이고 바뀌지 않는다.
- **파일 트리가 없다.** 디렉토리를 펼쳐 돌아다니는 UI는 만들지 않는다. 파일에 도달하는
  길은 검색뿐이다. 트리가 없으면 파일 관리자가 되지 않는다.
- **정확한 "정의로 가기"가 없다.** 언어 서버를 붙이지 않는다. `git grep` + 선언 모양
  판별로 추정하는 방식을 만들어 봤지만 정확도가 기대에 못 미쳐 되돌렸다. 정확한 심볼
  이동이 필요하면 그때는 IDE를 쓰는 게 맞다.
- **디버거·리팩토링·자동완성이 없다.** 앞으로도 없다.
- **원격 조작이 없다.** push/pull/rebase/reset은 터미널이 더 빠르고, 잘못 누르면
  되돌리기 어렵다. 쓰기 동작은 stage/unstage/commit까지다.

`git`이 아는 파일만 다룬다(`git ls-files`, `git grep`). 그래서 `.gitignore`가 자동으로
지켜지고 `node_modules`가 검색 결과를 덮지 않는다.

| v0.2 | 커밋 히스토리 — 브랜치 그래프, 커밋 상세, 브랜치·커밋 검색 |

| v0.4 | **AI 리뷰 루프** — 기준점, 개별/전체 확인, 코멘트→프롬프트, 위험 신호 |
| 이후 | UI를 Apple 플랫폼 재료로 재설계, **한 줄 보기(inline diff)** — 터미널 옆 좁은 폭 |
| v0.5 | **AI와의 소통** — 이미지 미리보기, 리뷰 스레드(반영 추적), 컨텍스트 담기, 사이클 요약 |

v0.5는 원래 "커밋까지 브라우저에서 끝내기"였는데 **방향을 다시 잡았다.** 이건 git
IDE가 아니다 — 커밋 메시지를 쓰는 것도 결국 AI라서, 브라우저에 커밋 UI를 만드는
값이 낮다. 대신 리뷰를 AI에게 넘기고 되짚는 쪽으로 갔고, 그 네 가지(이미지 미리보기 ·
리뷰 스레드 · 컨텍스트 담기 · 사이클 요약)를 마쳤다. 자세한 계획은
[ROADMAP](ROADMAP.md), 기준은
[CLAUDE.md](../CLAUDE.md#이건-git-ide가-아니다-2026-07-26-방향-확정).

## 7. 코드에 손댈 사람에게

```
bin/grmide.js      CLI — 저장소 루트 탐색, 포트 확보, 터미널 요약, 브라우저 실행
server/            Express. git은 항상 execFile로 인자 배열 전달 (셸 금지)
  git.js           git 명령 래퍼
  diff.js          unified diff → 나란히 보기 행 구조 (순수 함수)
  log.js           git log 파싱 + 그래프 레인 계산 (순수 함수)
  risks.js         위험 신호 판별 (순수 함수)
  preview.js       그림으로 볼 수 있는 형식 판단 (순수 함수)
  resolve.js       코멘트가 반영됐는지 판정 (순수 함수)
  context.js       컨텍스트 프롬프트 조립 (순수 함수)
  cycle.js         사이클 요약 조립 (순수 함수)
  state.js         코멘트·확인 표시 저장 + 프롬프트 생성
web/src/           Vue 3 SFC. 상태 관리 라이브러리 없음 — composables로 충분하다
  inline.js        나란히 행 → 한 줄 목록 펼치기 (순수 함수)
  highlight/       문법 강조 플러그인 (언어 추가는 여기 파일 하나)
test/              순수 로직만 테스트. npm test
```

읽는 순서를 추천하면 이렇다.

1. **[ARCHITECTURE.md](ARCHITECTURE.md)의 "설계 결정" 절** — 코드보다 이걸 먼저 읽는 게
   빠르다. "왜 이렇게 했는지"가 전부 여기 있다. 특히 겪었던 버그와 그 이유가 적혀 있어서,
   같은 함정을 다시 밟지 않게 해준다.
2. **[CLAUDE.md](../CLAUDE.md)** — 범위 규칙(무엇을 넣지 않는가)과 문서화 규칙.
   코드를 바꿀 때 어떤 문서를 함께 갱신해야 하는지가 표로 있다.
3. **[API.md](API.md)** — HTTP 엔드포인트와 응답 스키마.

작업 규칙은 두 개만 기억하면 된다.

- **문서를 같은 변경 안에서 갱신한다.** 문서가 코드와 어긋난 상태로 커밋하지 않는다.
- **설계 판단을 바꿀 때는 왜 그렇게 했는지를 남긴다.** 결론만 적으면 나중에 되돌릴
  근거가 사라진다.

검증은 이렇게 한다.

```bash
npm test        # 파서·강조·위험 신호 등 순수 로직
npm run dev     # 서버(4317) + vite(5173)
```

**서버·UI를 바꿨으면 임시 git 저장소를 만들어 실제로 띄워 확인한다.** API가 200을
돌려주는 것으로는 부족하고, 화면에 제대로 그려지는지까지 본다 — 이 프로젝트에서 실제로
잡힌 버그 대부분이 그 단계에서 나왔다.
